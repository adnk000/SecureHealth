A secure medical records system focused on confidentiality, integrity, and accountability.

🛡️
Confidential Access
Data visibility strictly depends on user clearance level. Sensitive patient records remain protected through enforced security policies at every request.
🎭

⚡

03 / 10 — Security Model

🔒 Bell-LaPadula

Applying formal academic security theory in a practical hospital database context.

📖 No Read-Up Lower-clearance users cannot view records classified above their level. An intern cannot read a confidential patient record — enforced at every route.
✍️ Restricted Write Access Only Level 3 users can edit patient records. This prototype restricts editing by role; it does not claim to implement the complete Bell-LaPadula *-property.
🏷️ Clearance Labels Every user and every record carry explicit security labels. Enforcement is consistent, automatic, and logged for auditing purposes.
🧪 Policy Enforcement Server-side checks compare the user's clearance with each record's classification before returning protected data.
04 / 10 — Access Roles

👤 User Roles

Three tiered access levels mirroring realistic hospital staffing hierarchies.

🧑‍⚕️
Level 1 — Intern
Read low-sensitivity records only. Patient names are automatically masked. Cannot modify any data. No audit log access.
👩‍⚕️
Level 2 — Nurse
View records classified at Level 1 or 2. Cannot modify records or access security logs. Names are not masked at this level.
🩺
Level 3 — Doctor
Read access to all three record levels and permission to edit records. Can export audit logs as CSV.

Clearance scale: Intern → Nurse → Doctor

05 / 10 — IDS

🚨 Intrusion Detection

Monitoring suspicious behavior and protecting system integrity in real time.

❌
Failed Login Tracking
Every invalid login attempt is timestamped and stored with the submitted username and event type in the security log table.
📤
Audit CSV Export
Doctors can download a full security audit as a machine-readable CSV, enabling integration with SIEM tools or compliance reporting pipelines.
🆘
Break-Glass Override
Emergency-access requests are recorded for review. A request never changes the user's clearance level.
🔎
Real-Time Alerts
Dashboard surfaces recent suspicious events. Recent security events are displayed to Level 3 users for manual review.
06 / 10 — Privacy

🕵️ Patient Privacy

Reducing exposure of sensitive information under lower-clearance access through automated controls.

🪪
PII Protection
Patient names are automatically masked for interns. The masking logic runs server-side — the client never receives raw PII for unauthorized roles.
🔑
Password Hashing
All user credentials are hashed with a secure algorithm before storage. Plaintext passwords never persist in the database at any point.
🎛️
Scoped Dashboard Views
The dashboard filters records in real time based on clearance rules. Users see only what they are authorized for — no client-side filtering tricks.
🛂
Session Management
Flask's signed session cookie maintains login state. HttpOnly, SameSite, and a configurable secure-cookie flag help protect the session.

08 / 10 — Implementation

⚙️ Implementation

Tech stack, security mechanisms, and design decisions behind SecureHealth.

🐍 Backend Python 3 + Flask deliver routing, auth, and session management. Jinja2 templates render role-aware views server-side for zero client-side data leaks.
🗄️ Storage SQLite provides a lightweight embedded database. Separate tables for patients, users, audit logs, and security labels keep concerns cleanly separated.
🔐 Security Server-side clearance checks, Werkzeug scrypt password hashing, CSRF tokens for POST requests, and hardened Flask session-cookie settings.
📋 Compliance Audit logs capture timestamp, actor, action, and outcome. CSV export enables integration with hospital compliance and reporting workflows.
